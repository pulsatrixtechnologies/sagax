   MCP cases read `config.json` `mcpServers` and reset it between tests.
   The servers (and their secret env) now live in the sealed installation
   store, so config.json no longer has them and a reset no longer clears
   them (a second leftover server shows in the list). Update the tests to
   read and reset through the store or the API.

   `server/org-harness-commands.e2e.test.ts` "uses the room speaker's Me
   skills". Root cause: commit 9ede65b25 (lot 5 wiring) made
   `readSkillLibraryIndexState` / `writeSkillLibraryIndex` in
   `server/skill-library.ts` ignore their `root` once the installation store
   had absorbed `skills-library-index` (which the boot migration marks on
   the very first boot, file or not). `PersonalSkills` passes a per-person
   root (`principals/<pid>/capability-skills`), so every person's Me index

   PUT or DELETE edited or removed Alice's entry; Me skills also showed in
   the organization's `/api/skills-library`. Fix: the bridge applies to the
   installation root only (`installationLibraryBridge`); one-time repair
   `skills-library-person-split` moves misplaced entries back under their
   person (dev builds only; nothing in production). Audit of the other lot 5
   data: personal plugins (`personalPlugins` uses `storage` =
   capabilities.enc, no `capabilityStore`), personal MCP servers and
   secrets (`PersonConnections`, capabilities.enc), person capability
   choices (capabilities.enc) and bot stores (`bot-capabilities/<botId>/`)
   were not routed through the installation store; `orgCapabilityMarkets`
   has no `installationStore`. Regression tests: `server/skill-library.test.ts`
   (fails on the old code with the same 422), the migration repair in
   `server/capabilities-store-migration.test.ts`, and a two-person case in

   `config.json` and from any plaintext file).
