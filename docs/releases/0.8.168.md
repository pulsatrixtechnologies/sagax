Sagax 0.8.168 est un correctif pour Sagax de bureau. La page Personal s'ouvre de nouveau sur l'app au lieu de rester prise sur l'écran du code d'appairage, et les appels internes de l'app vers ton serveur local gardent leur capacité desktop. Un fichier qu'un bot télécharge atterrit maintenant dans tes dossiers à toi, jamais sur le serveur Sagax.

### Ce que tu remarques d'abord

* **La page Personal s'ouvre sur l'app** : dans un Sagax de bureau en mode serveur, la page Personal repartait sur l'écran du code d'appairage. La fenêtre du desktop rouvrait l'adresse où elle était restée, donc une seule visite sur cet écran y laissait la page pour toujours, même quand ton serveur local tient cette machine pour son propriétaire. Personal repart maintenant sur l'app, et l'écran d'appairage ne revient que quand le serveur le demande vraiment (#5160).
* **Les appels internes de l'app gardent l'accès** : depuis 0.8.167, les appels GET que la page de l'app envoie à son propre serveur local perdaient l'en-tête de capacité desktop et repartaient en « sign in required ». La page Personal sautait alors sur l'appairage, et les previews de fichiers comme les flux en direct de la page de l'app échouaient aussi. La page de l'app garde maintenant sa capacité sur ces appels, POST comme GET, sans jamais l'accorder à un simple navigateur de cette machine (#5162).
* **Un fichier téléchargé par un bot arrive chez toi** : quand un connecteur renvoie un fichier binaire (une pièce jointe de ticket, un document), le bot l'écrivait dans son propre dossier sur le serveur Sagax, hors de portée : il ne pouvait ni le poster dans le chat ni le copier sur ton ordinateur. Le fichier est maintenant déposé dans l'endroit qui t'appartient pour ce tour (le dossier des pièces jointes de l'app desktop en priorité, sinon l'environnement du serveur), et le bot le relit depuis là pour le poster ou te le donner. Un chemin sensible (dossier caché, fichier de credentials) reste refusé, comme partout ailleurs (#5138).

### Sous le capot

* Les appels GET internes de la page de l'app sont reconnus comme venant de l'app d'après l'origine qui les émet, une fois l'en-tête `Origin` absent. Chromium n'envoie pas cet en-tête sur un GET de même origine, et la page de l'app est servie sans `Referer` : c'était la cause du refus. Un navigateur de la machine, une frame d'une autre origine ou une page sous sandbox ne portent toujours pas la capacité (#5162).
* L'écriture d'un fichier de connecteur dans tes dossiers et la reprise d'un fichier téléversé partagent maintenant une seule voie de copie, la même que l'app desktop utilise pour ses propres pièces jointes (#5138).

### Avant de mettre à jour

Rien de spécial. Si tu héberges Sagax toi-même, garde une copie de tes données (`docs/self-hosting.md`) avant de remplacer l'image ou le binaire. Un fichier qu'un bot télécharge ne s'écrit plus sur le serveur mais chez toi : un bot qui comptait relire ce chemin côté serveur le relit maintenant depuis ton ordinateur ou l'environnement du serveur.

## English

Sagax 0.8.168 is a fix release for the Sagax desktop. The Personal page opens on the app again instead of staying trapped on the pairing code screen, and the app's own calls to your local server keep their desktop capability. A file a bot downloads now lands in your own places, never on the Sagax server.

### What you notice first

* **The Personal page opens on the app**: on a desktop Sagax in server mode, the Personal page kept opening on the pairing code screen. The desktop window reopens the address it was last on, so a single visit to that screen left the page there for good, even when your local server holds this machine as its owner. Personal now goes back to the app, and the pairing screen only comes back when the server really asks for it (#5160).
* **The app's own calls keep their access**: since 0.8.167, the GET calls the app's page sends to its own local server lost the desktop owner header and came back as "sign in required". The Personal page then jumped to pairing, and the app page's file previews and live streams failed too. The app's page now keeps its capability on those calls, POST and GET alike, without ever granting it to a plain browser on this machine (#5162).
* **A file a bot downloads lands with you**: when a connector returns a binary file (a ticket attachment, a document), the bot wrote it into its own folder on the Sagax server, out of reach: it could neither post it in the chat nor copy it to your computer. The file is now placed in the spot that is yours for this turn (the desktop app's attachments folder first, otherwise the server environment), and the bot reads it back from there to post it or hand it to you. A sensitive path (a hidden folder, a credential file) stays refused, as everywhere else (#5138).

### Under the hood

* The app page's internal GET calls are now recognized as coming from the app by the origin that issues them, once the `Origin` header is absent. Chromium sends no such header on a same-origin GET, and the app page is served with no `Referer`: that was the cause of the refusal. A browser on the machine, a frame from another origin or a sandboxed page still never carry the capability (#5162).
* Writing a connector file into your places and reading back an uploaded file now share one copy path, the same one the desktop app uses for its own attachments (#5138).

### Before you update

Nothing special. If you host Sagax yourself, keep a copy of your data (`docs/self-hosting.md`) before replacing the image or the binary. A file a bot downloads no longer lands on the server but with you: a bot that used to re-read that server path now reads it back from your computer or from the server environment.
