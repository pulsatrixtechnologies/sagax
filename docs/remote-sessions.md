# Remote sessions

A connected Tailcat session shows up in the bot panel under Sessions à distance and as a card in the chat. The section is always in the panel: with no session it says so in one line. Each row shows the computer, the user, the support code and the end time, with Prendre le contrôle (Windows) and Fermer la session (a second click confirms). In the chat, the session is the bot computer's own screen card first (`RemoteScreenCard` on `ComputerScreen`: the live picture, Prendre le contrôle in the middle on intent, Play / Pause / Stop at the bottom, « Écran de <POSTE> » under it; Pause stops the picture, Stop ends the session on a second press), then the facts card (name, user, rights, support code, end time; serial, model, processor, memory and disk folded) with short diagnostic hints. The hints send a prompt. They do not run a command by themselves. A server without a desktop (Windows Server Core, a Linux server: the inventory's `gui=false`) has no screen card; its facts card says « Serveur sans interface : shell seulement ».

When the facts are not there, the card says why instead of n/a (`view.inventory`): « Inventaire en cours », « Session ouverte hors de Sagax » (this server does not have the tunnel), « Le poste ne répond pas » (Sagax asks again every 30 s, on the panel's poll and on the screen's), « OS inconnu » with Windows / macOS / Linux buttons for the technician (`POST .../os`), or « Ce serveur Sagax n'a pas de client ssh ». On a Mac, a refused screenshot (Screen Recording not allowed for the Terminal that runs the session) says so.

Shell opens the existing in-chat terminal on that computer. Send a file (up to 8 MB) and Download move one file through the tunnel. Prendre le contrôle, from the screen card or the panel row, opens the bot computer's own window (`SandboxDesktopModal`: « Écran de <POSTE> », « En marche · Vous avez le contrôle », Rendre le contrôle, Play / Pause / Stop, full screen, close), never the Computer tab. The window opens a control WebSocket (`/api/bots/:id/remote-sessions/:id/control`, same upgrade path as the terminal), a small user-mode helper runs over the tunnel (on Windows: PowerShell with a compiled C# input loop, `SendInput` for input and `CopyFromScreen` JPEG frames, standard rights, no admin, nothing installed; macOS and Linux stay view-only until the signed helper app). The tunnel command is a short bootstrap and the program travels on stdin, so no command-line length limit applies. The helper writes no files of its own, but `Add-Type` compiles into the user's temp folder, PowerShell script-block logging (event 4104), when an admin enabled it, records the script, and antivirus may inspect it. On the end user's screen an always-on-top notice says control is in progress and names the technician; the technician sees « Vous avez le contrôle » in the window, and input leaves only while control is held; Rendre le contrôle sends one grant message and the frames go on. Closing the window, losing focus, or closing the session lifts every held key and button, closes the helper's stdin and stops it; the helper also stops on the end-user script's stop file and at its deadline. Every control action (start, notice shown, grant, release with activity counts, stop) is audited in `DATA_DIR/remote-control.jsonl` (rotated at 8 MB) without logging the keys. Closing the session asks the end-user script to stop, then marks the card closed.

The tunnel address and the client key stay in the Flow session folder (`$PX_FLOW_HOME/tailcat/<12 hex>/`, default `~/.pulsatrix-flow`). Sagax reads that folder on this host. They are never tool arguments, never API fields, and never shown. If the folder is missing, the card can still show the facts the bot supplied, and shell, files and the screenshot say the tunnel is not on this server.

A session the bot opens with `remote_support_open` (the agents catalog tool, or a Perspicax profile the engine mounts) is registered by Sagax itself: every `remote_support_*` answer passes through `PerspicaxMcp.relay`, and `server/remote-session-register.ts` posts the card and the panel row as soon as `remote_support_status` says connected, and marks it closed on `remote_support_close`. The session id, rights, OS and end time come from the open call; nothing reads the address from a tool answer. For a session Sagax opened, the tunnel is in `<data dir>/remote-support/sessions/<CODE>/` with the technician key beside it. When the OS was not named, Sagax takes the one the support page detected when the connected status says it, else asks the computer (`uname -s`, then `[Environment]::OSVersion.Platform`, which only PowerShell answers with Win32NT), outside the store's lock. An answer that is neither is not Windows: the OS stays unknown, the card says « OS inconnu » and Sagax asks again (session 8F2NZU, a Mac shown as Windows, 2026-10-22).

Every command for Windows travels as `powershell.exe -EncodedCommand`: the Tailcat session shell on Windows is PowerShell itself, so a script in a double-quoted `-Command "..."` lost its `$variables` to the outer shell (empty inventory, no screenshot, no transfer folder, no stop file, no live control). `tailcat ssh` and `tailcat cp` exec the system ssh client, so the server image installs `openssh-client`; without it the card, the shell and the bot's tools say so.

The bot has two direct tools on a connected session (`server/remote-session-exec.ts`): `remote_session_snapshot`, one fixed read (OS, uptime and load, CPU, memory, disks, top processes) in one call, and `remote_session_exec`, one command with its exit code, stdout and stderr (64 KB each, 30 s by default, 120 s at most). On macOS and Linux, a command that only reads (`shared/read-only-command.ts`, #875) runs without a card; any other is a card every time, which no level, rule or Always allow answers. On Windows, and on a computer whose OS is not known yet, every command asks: that classifier is POSIX, and PowerShell quoting, drives (`env:`) and providers would pass it (security review of #965, until a PowerShell classifier with a cmdlet allowlist exists). The classifier also refuses a carriage return, control characters, Unicode quote and space lookalikes, secret paths written with backslashes, PowerShell drives and provider paths (`::`), and network paths anywhere in the line. The route checks again behind the approval hook: a command that does more than read runs only after the person allowed that exact command in that conversation, once, within ten minutes (`consumeRemoteExecApproval`). No command runs while the OS is still guessed. What the computer prints goes back to the model fenced as untrusted data.

How the commands reach the computer: `tailcat ssh` execs the system ssh client with its own options (ProxyCommand through tailcat, `StrictHostKeyChecking no`, `UserKnownHostsFile /dev/null`, `LogLevel ERROR`, read from the tailcat 0.7.0 binary). The host key is not pinned by ssh because the peer is already authenticated by its node key inside the WireGuard tunnel the address names; nothing is written to a known_hosts file in the container. The remote command is one argv element (execFile, no local shell) and is parsed once, by the remote shell. Extra ssh options cannot be passed (anything after the address is the remote command), so Sagax removes `SSH_AUTH_SOCK` and `SSH_AGENT_PID` from every tailcat child (`tailcatEnv`): no agent to offer or forward. The server image holds no ssh identity of its own; ssh may still offer a default public key of the server user if one existed, which the no-auth server ignores. A session a Flow skill opened is posted with `publish_remote_session` once the end user is connected.

A session belongs to the person whose Perspicax credentials opened it, and to that bot. `remote_support_open` writes `principalId` and `botId` into `sessions/<CODE>/open.json`. The owner is read only from the owner the Sagax server attaches to the `/api/internal/perspicax/tool` answer (`PerspicaxMcp.turnPrincipal`), never from the proxy's environment: the engine launches that proxy, so a `SAGAX_REMOTE_SUPPORT_PRINCIPAL` env is not trusted and no longer set. A tunnel resolves only through the row's own code folder, whose `session` file holds the row's id and whose owner matches the row's person and bot; a folder without an owner never resolves. The 12-hex id is on the chat card, so it is useless on its own: `publish_remote_session` and a direct open refuse an id another person or bot opened, the registrar and its restart recall follow the speaking person (never the conversation owner), and the end time is bounded to 26 hours on every path. `remote_support_status` and `remote_support_close` are checked against the code folder's owner on the server before Perspicax is called, so a call for someone else's session never reaches Perspicax; a folder with no recorded owner is refused to everyone. Fermer la session in the panel deletes the local `address` file and leaves a `closed` marker first, so even if Perspicax cannot be reached the tunnel no longer resolves here and a late "connected" status cannot write the address back or re-open the card. A Flow session folder (`~/.pulsatrix-flow/tailcat/<id>`) carries no owner until its first publish: it is then bound to that person and bot in `owner.json`, and a later publish or tunnel read by anyone else is refused. Ended rows and support folders untouched for 48 hours are pruned, and the support-folder scan is cached by directory mtime instead of re-read on every publish and close.

The technician key (`<data dir>/remote-support/technician.private.json`) and the session addresses stay in that folder. On an organization server the engines run in the Sagax container as the same user, so the folder is on their filesystem; tool withholding already keeps the built-in engines away from it, and a `permissions.deny` on Read, Glob and Grep of that folder is added to every non-guest Claude turn as a second layer (`server/engine-protected-paths.ts`). This does not cover a Bash `cat` on a solo desktop, nor every engine; the robust fix (keep the key off the engine host, or forward the remote-support calls through an internal server route so only the Sagax process handles the key) is a JC decision noted in the stage-2 PR.

## The fast process the bot follows

1. A session without administrator rights by default. Elevated only when the person asks.
2. At most three calls: `remote_support_open`; when the person says the script is launched, `remote_support_status` (fetch_ip_count must be exactly 1, one address took the script); that same status connects and marks the session connected (once more if it still says started). No schema search, no cloud fallback.
3. The first reply holds the link, the code and the normal PowerShell line in a `powershell` code fence, exactly as the tool gave it. The line never goes through a shell on this computer: a Mac shell eats its `$` variables.
4. No screenshot written to the Desktop, no Preview: the screen is drawn in Sagax.
5. Never expose the person's own computer: no `tailcat serve`, no exit node, no file sharing, no tunnel back to it. A shell request that names no other destination opens the remote terminal at once.

Sagax ships tailcat 0.7.0 beside the app and in the server image. It runs that copy, then a copy under its data directory, then Homebrew or `/usr/local/bin`. A tailcat on the default system PATH is not required, and Sagax does not download one at runtime. The server image and the cloud computer image bake the Linux binary into `/usr/local/bin`. A cloud computer that is already running does not see it until that image is rebuilt and published.
